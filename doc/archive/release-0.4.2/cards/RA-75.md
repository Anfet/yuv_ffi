# RA-75 — Workflow Android
**Status:** DONE · **Tier:** T2 · **Owner:** Terra (Integration Executor) · **Execution Mode:** STANDARD · **Review Tier:** T1 · **Depends On:** RA-70 · **Rejection Count:** 1

#### Problem / Goal
Вынести джобу `android-native-build` из общего `ci.yml` в отдельный workflow: он запускается только на свои пути и не зависит от чужих платформ.

#### Architect Decision
По соглашениям RA-70.
- Файл `.github/workflows/ci-android.yml`, одна джоба, раннер `[self-hosted, Windows, X64, android-emulator]`.
- В YAML только checkout, выбор раннера и вызов `tool/ci/android.ps1` (Linux — `.sh`). Логика — в скрипте.
- Скрипт выполняет: APK arm64/armv7/x86_64 и проверка состава ABI; на AVD `Tablet` — smoke и `*_native_test.dart` через `tool/ci/drive`.
- Маршрут по префиксу ветки (RA-53): `all/**` и ключ этого workflow; `release/**`/`main` — всегда. Пути платформы (`src/**`, `android/**`, `lib/src/yuv/impl/io/**`, `test/probe/**`, `example/integration_test/**`, `example/android/**`) должны совпадать с картой `tool/ci/scope_guard.sh`; расхождение правится в карте, а не в workflow.
- На момент решения `release/0.4.2` (`5a0f4126bb971d2eaa727cbc672c3a21859c4cf7`) не содержит ни `ci-android.yml`, ни `android.ps1`. Отрицательный push от этого SHA не проверяет Android workflow. Перенос workflow в ветки `docs/**` или `windows/**` сделал бы их суммарный diff несовместимым с `scope_guard.sh` и правилом о Markdown-only ветке `docs/**`.
- Проверка делится на два рубежа. Для `REVIEW`/`ACCEPTED` свежий Executor создаёт ветку реализации `all+android/RA-75-attemptN` непосредственно от актуального `origin/release/0.4.2`, переносит в неё только изменения RA-75 с учётом уже интегрированных workflow, выполняет локальную проверку и получает зелёный `CI Android` по push. Старую ветку реализации нельзя считать актуальной release-базой. При движении release-базы до интеграции кандидат обновляется от нового HEAD и проверяется повторно.
- После независимого принятия реализация интегрируется в `release/0.4.2` по обычному разрешённому процессу. Свежий Executor интеграционной валидации создаёт от точного интегрированного SHA, где уже присутствуют `ci-android.yml` и `android.ps1`, две отдельные контрольные ветки: `docs/RA-75-md-control-attemptN` с одним изменением `*.md` и `windows/RA-75-foreign-control-attemptN` с одним безвредным файлом `windows/.ra75-routing-control.txt`. Они не сливаются в release. Контрольные push должны показать отсутствие `CI Android`; на Windows-ветке должен появиться `CI Windows` с успешным `Check branch scope`.
- Отрицательные контроли относятся к интеграционной валидации RA-75. Для каждого сохранить SHA базового release, ветку, SHA push, время UTC, ссылку на проверяемый список runs и отсутствие Android run для этого SHA. До этих доказательств и успешного полного release CI на точном SHA реализации карточка не переходит в `DONE`.

#### Scope
`.github/workflows/ci-android.yml`, `tool/ci/android.*`, удаление джобы `android-native-build` из `ci.yml`; после интеграции — две временные ветки для отрицательных routing controls. Чужие workflow и скрипты не трогать; контрольные коммиты в release не сливать.
