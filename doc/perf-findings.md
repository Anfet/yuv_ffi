# yuv_ffi — выводы по производительности (0.4.x)

Сводка замеров 25–28.09.2026. Сырые данные, патчи кандидатов и полные отчёты удалены из рабочего дерева; они есть в git на `e801bb6` в `doc/archive/perf/` (`git show e801bb6:<путь>`).

## Как мерить, чтобы не обмануться

- **Только release/AOT.** `flutter drive --profile` завышает стоимость native FFI вызова в 3–8 раз: rotate на Pixel 3 — ~94 мс в profile против 15 мс в release. `integration_test` на мобильных работает только в profile, поэтому числа для решений берутся из release-стенда внутри приложения.
- **Pixel 3: экран включён, keyguard снят.** С выключенным экраном `toBgraBytes()` 720×360 занимал 43–46 мс вместо 11 мс.
- **A/B — чередованием, не блоками.** Блочный порядок давал «выигрыш» 3,6–9%, который при перемешанных A/D прогонах исчезал и менял знак (BGRA-04).
- **Подготовка входа, clone источника и проверка checksum — вне таймера.** Checksum результата сравнивается на каждой строке; побайтное равенство с oracle обязательно для любого fast path.
- **Windows:** один план питания и affinity (`0x4`) на обе стороны; на этой машине доступны только Balanced и Power saver, поэтому Windows-числа — диагностические, не baseline. SHA-256 DLL между пересборками MSVC не совпадает (временные метки) — это не дефект.

## Native kernels ABI v1

- **Причина регрессии 0.4 против 0.2.4:** общий попиксельный драйвер `yuv_kernel_v1.c` — косвенный `map()` на пиксель и `yuv_checked_sample_offset` (две деления `SIZE_MAX / b`, не инлайнится) на каждый sample. Blur декодировал кадр в RGB и считал полное 2D-ядро `(2r+1)²` дважды на пиксель. Итог — flip/convert в 10–350 раз медленнее 0.2.4.
- **C-01…C-11 добавили tight fast paths** (Windows Release, до → после): flip V до 426×, convert I420→I420 410×, crop aligned 734×, rotate ~10–11×, grayscale ~13–15×, black-white 11–30×. Padded/gapped layout остаются на общем пути.
- **Итог против 0.4.0** (PROBE 1, AOT Release, медиана 9 вызовов, 12 операций × 1920×1080 и 720×360): Windows x64 и Pixel 3 arm64 быстрее на 52–94 % во всех случаях, замедлений нет (convert I420→BGRA 1080p: 191,7 → 36,9 мс Windows, 101,4 → 26,7 мс Pixel 3; gaussianBlur — наименьший выигрыш, 58–65 %). Таблица — `git show 3962d7c:doc/archive/release-0.4.2/ra26-windows-release/README.md`, baseline — `test/probe/baseline/`.
- **Fast path включается, только если все плоскости плотные** (`pixelStride == sampleBytes` и нет row padding). Одна неплотная плоскость отключает его для всей операции.

## YUV → BGRA

- Windows 1920×1080, полный публичный вызов: NV12 43,2 → 30,0 мс (−30,5%), I420 43,7 → 30,5 мс (−30,1%). Pixel 3 после подготовки кадра: NV12 8,50 → 6,30 мс, I420 8,25 → 6,85 мс.
- Что дало выигрыш: ускоренные NV12/I420 ветки kernel и `malloc` вместо `calloc` для полностью перезаписываемого tight destination (для padded/gapped остаётся `calloc`: иначе в padding неинициализированная память).
- Раскладка после цикла: kernel ~51%, staging ~27%, copy-out ~13%, выделение памяти <1%. Следующий кандидат — снова kernel; альтернативный copy-out (`ByteBuffer` view + `sublist`) выигрыша не дал.

## Dart-копирование

- Построчный `setRange` вместо посэмпльного копирования при плотном pixel stride (в production): ROI seed 49,4 → 27,2 мс, copy-back `applyTo` 45,2 → 11,8 мс на padded BGRA 1080p. Row padding назначения не трогается; gapped pixel stride идёт прежним путём.
- `applyPatch`, Pixel 3 release, назначение 1920×1080, медиана 30 после 5 прогревов, мкс (`64×64 / 256×256`): I420 tight `3 / 20`, padded `3 / 21`; NV12 tight `2 / 17`, padded `2 / 16`; BGRA tight `2 / 27`, padded `2 / 28`. Tight I420 256×256 значительно быстрее порога 2 мс; native-карточка не нужна.

## Кадры камеры

- На Pixel 3 `ImageFormatGroup.yuv420` отдаёт U и V с `bytesPerPixel == 2`: это чередующийся буфер NV12/NV21, показанный как две плоскости. Снятие одного row padding оставляет `pixelStride == 2`, и fast path не включается.
- Полная упаковка при импорте (`pack()`, плотный импорт камеры по умолчанию) на Pixel 3 720×480 в release: rotate 15,0 → 4,5 мс (3,3×), показ 15,7 → 19,3 FPS, `dropped_busy` 48% → 36%. На других устройствах не измерялось.
- Pixel 3, release, SHA `053307e`, фронтальная камера medium 720×480: повторный Device check показал 29,8 FPS без
  обработки и 28,9 FPS с обработкой раз в секунду; Gaussian blur — 13 запусков за 15 с, медиана 439,5 мс.
- Все шаги DEVICE 2 прошли: поворот, зеркало, рамки лиц и `capture.answer == true`; снимок в портрете — 474×720.
  Это выше VIEW-04 (20,4–21,1 FPS из 30); по итогу PASS прототип VIEW-04 удалён в пуле `STAGE5-DEVICE`.

## Web

- Chrome 154, Windows, i9-13980HX, release dart2js, кадр 1280×720 (WEB 6…8, `doc/web-camera-yuv.md`): до WEB 5 показ YUV через `YuvFrameRenderer.upload()` стоил 58 мс против 14 мс у BGRA: шейдер был выключен, кадр переводился в BGRA в WASM (`toBgraBytes()` ~38 мс, примерно в 3 раза медленнее native); декод в `ui.Image` — ~11,5 мс в обоих случаях. С шейдером (WEB 5) `upload()` I420/NV12 — 13,6/12,7 мс против 15,7 мс у BGRA, кадр через `YuvFramePresenter` — 16,8 мс (упор в 60 Гц) против 59–66 мс через BGRA-путь. Камера отдаёт `NV12`, `copyTo` без `format` — 4,3 мс против 10,3 мс у BGRA; импорт в `YuvImage` — 1,4–1,6 мс в любом формате.

## Blur (эксперименты, в production не перенесены)

- Базовая линия Pixel 3, release: Box/Mean 8,6 мс (720×360) и 54,9 мс (1477×1065); Gaussian r10 — 225 и 1427 мс. Box и Mean — одно и то же uniform-ядро.
- Blur напрямую по YUV вместо RGB: Box Y/U/V −67…−70%, Y-only −77…−80%. Gaussian 2D по Y/U/V −34%.
- Разделимый Gaussian по Y/U/V: 186 мс против 938 мс у прямого 2D (5×), побайтно совпадает с 2D YUV; scratch 242 КиБ при 1477×1065/r10.
- Открытый вопрос контракта: blur по YUV визуально отличается от текущего blur в RGB (Y-only меняет поведение заметно, Y/U/V — почти неразличим на эталонном кадре). Перенос в production требует решения о семантике.
