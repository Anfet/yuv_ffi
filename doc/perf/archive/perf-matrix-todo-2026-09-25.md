# yuv_ffi 0.4.2 — открытые задачи

Выпуск 0.4.1 отменён до публикации и создания тега. Следующая целевая версия — 0.4.2 с ускорением всей матрицы ABI v1. Принятые проверки кандидата 0.4.1 остались историческими свидетельствами в `COMPLETION.md`; они не являются приёмкой 0.4.2.

AUD-21 (финальные gates отдельного выпуска 0.4.1) отменена; её актуальный смысл перенесён в PERF-38 для 0.4.2. До завершения MEAS-01/02, всех выбранных пооперационных MEAS-карточек и PERF-01—37 нельзя считать 0.4.2 готовой к публикации. Операция для каждой MEAS-карточки выбирается при старте соответствующей PERF-карточки.

## Историческая предпроверка кандидата 0.4.1 (2026-09-25)

- База: чистый `35c516e216fef8d5ed4ef379d38655fc643f738d`. Локально прошли `flutter analyze`, 639 тестов, `dart format --output=none --set-exit-if-changed lib test example/lib example/integration_test` (0 изменений) и `flutter pub publish --dry-run` (0 warnings, 1 ожидаемый advisory hint о скачке версии с 0.2.4). WASM assets входят в архив, внутренние трекеры исключены. Локальный `flutter pub get` переписал `example/pubspec.lock`; этот след проверки откатан, рабочее дерево оставлено чистым.
- [CI run 36117003942](https://github.com/Anfet/yuv_ffi/actions/runs/36117003942) на этом SHA завершился с общим `success`: 11 job прошли; неблокирующий `android-armv7-runtime` завершился `failure` на известном нестабильном handshake эмулятора. Принятие ARMv7 runtime опирается на физический Pixel 3 из AUD-17, а не на зелёный статус эмулятора.
- Поздняя предпроверка на изменённом дереве прошла analyzer, 639 тестов и проверку форматирования, но dry-run получил warning из-за незакоммиченных `CHANGELOG.md`/`README.md`. Эти результаты и CI прежнего SHA не подтверждают будущий 0.4.2.

## 0.4.2 — производительность ABI v1

Цель: максимально ускорить всю матрицу операций на IO и Web до уровня, **сопоставимого с 0.2.4 или лучше**, без изменения публичного ABI v1 и результата, заданного `doc/api-abi-0.4-design.md`. Ядра 0.2.4 служат источником алгоритмических приёмов (строчный обмен, прямые проходы, скользящие суммы, разделимая свёртка) и ориентиром по времени, но не эталоном байтов: с тех пор изменились семантика blur, обработка odd geometry, padding, цветовое преобразование и гарантии атомарности. Возврат к поведению 0.2.4 не входит в эти задачи.

Отправная точка — предоставленный пользователем независимый C-стенд: MSVC `/O2`, x64, I420, одинаковые входы и параметры операций. Для 1080p он сообщил 0.2.4 → ABI v1: vertical flip 0.46 → 106 ms, I420→BGRA 13 → 171 ms, box r=10 17 → 5978 ms, mean r=10 274 → 5947 ms, Gaussian r=10 166 → 8585 ms. Это свидетельство регрессии и набор гипотез, **не воспроизведённый здесь релизный benchmark**. Показатель «39» у отдельной операции в example подписан `msec`; время blur большого снимка следует измерять отдельно.

### Порядок работ и проверок

1. **Подготовка.** PERF-01 зафиксировал входные данные и нативный Windows-стенд. MEAS-01 завершает измеритель публичного Dart-вызова на Windows; MEAS-02 готовит воспроизводимые измерители на Pixel 3 и Web. Подготовительные smoke-прогоны не считаются исходной матрицей операций.
2. **Старт любой PERF-02—31.** Выбрать одну операцию по приоритету и доступным данным. До её первой правки завести следующую свободную MEAS-карточку (начиная с MEAS-03), вписать выбранный PERF ID, точные сценарии/параметры, SHA текущего кандидата и 0.2.4, платформы и команды. Добавить ID этой MEAS-карточки в зависимость выбранной PERF-карточки. Снять и независимо принять адресный исходный замер на Windows, Pixel 3 и Web. Для недоступного пути зафиксировать `UNSUPPORTED` и причину. Следующая MEAS-карточка создаётся только при выборе следующей операции.
3. **Завершение выбранной операции.** После принятия её MEAS-карточки изменить операцию, проверить корректность и повторить те же сценарии на всех трёх платформах. Сравнить `0.2.4 → до → после` отдельно для каждой платформы и принять PERF-карточку. Только затем выбрать следующую операцию. Общую исходную матрицу всех функций заранее не собирать. Если общий helper затронул другие операции, сразу проверить и адресно перемерить их.
4. **Итог.** PERF-32/33 отдельно проверяют импорт кадра и preview на Pixel 3. PERF-34/35/36 сверяют накопленные пооперационные результаты с конечным SHA и повторяют только затронутые или спорные сценарии на соответствующей платформе. PERF-37 проверяет iOS/macOS/Linux и CI, PERF-38 сводит результаты и release gates. Числа разных устройств и сред не смешивать.

На Pixel 3 сохранять приложение, данные и разрешения: устанавливать новую сборку поверх прежней с тем же applicationId и подписью (`adb -s <serial> install -r <apk>`), не выполнять `adb uninstall`, `pm clear` и переустановку с очисткой. [Android Developers](https://developer.android.com/tools/adb) подтверждает, что `-r` заменяет приложение с сохранением данных. До/после проверять разрешение камеры. Если подпись или версия не позволяют обновить приложение поверх, зафиксировать препятствие и согласовать способ проверки до удаления приложения.

### Правила исполнения и измерений

- Карточка с одной операцией выполняется и принимается отдельно. После завершения и проверки одной карточки фиксируется её SHA, затем начинается следующая. Указанный tier задаёт уровень исполнителя и приёмщика; конкретная модель выбирается перед началом карточки. Если общий helper затрагивает соседние операции, исполнитель включает их в проверку и отдельные замеры; для независимого включения fast path в каждую операцию создаётся отдельная карточка.
- Для каждой PERF-02—31 приложить пооперационный отчёт **«0.2.4 → до → после»** отдельно для Windows, Pixel 3 и Web: SHA перед карточкой и после неё; устройство, ОС, компилятор/браузер, флаги release, формат, размер, strides, ROI/радиус; одинаковые входные байты и seed; warm-up и число повторов; raw timings, медиану и p95 либо разброс; отношения времён и контрольную сумму результата. На Windows измерять C-ядро и публичный Dart-вызов; на остальных платформах измерять доступные слои отдельно и явно называть слой. Время одной платформы не заменяет время другой. Недоступный путь помечать причиной, не выдумывать нулевое время или выигрыш без чисел.
- PERF-01 сохраняет общий реестр сценариев; при старте очередной операции выбрать из него только её строки и записать выбор в новой MEAS-карточке. Для первой карточки кандидат может быть `35c516e`, для каждой последующей **«до» означает непосредственный parent SHA выбранной PERF-карточки**, включая уже принятые изменения других операций. 0.2.4 остаётся фиксированным опубликованным ориентиром. Исходный замер принимается до первой правки, а после изменения повторяются те же платформы, конфигурации и входные данные. PERF-34/35/36 проверяют полноту накопленных отчётов, PERF-38 сводит их без смешивания чисел разных устройств.
- По завершении серии все разрешённые сценарии 11 ABI v1 entry points, направлений `convert`, flip, rotate и эффектов должны иметь собственные пооперационные результаты. Для каждой строки записывать статус поддержки, конфигурацию, время, разброс, коэффициент к 0.2.4 и checksum. Если 0.2.4 на платформе или конкретная функция не запускается, указать точную причину и не выдавать строку за подтверждённое достижение цели. На Web неподдерживаемую функцию отмечать `UNSUPPORTED` с результатом вызова; время для неё не выдумывать. Частичная поддержка Web не считается полным паритетом.
- «Сопоставимо» означает, что повторные замеры не показывают устойчивого отставания от 0.2.4 на одинаковой платформе, входе и пользовательских параметрах; «лучше» — устойчивое ускорение. Если различие уверенно выходит за разброс и новый путь медленнее, задача возвращается на доработку. Изменение семантики с 0.2.4 явно помечать, но не исключать такую строку из сравнения скорости. Корректность результата проверяется побайтно по текущему эталону ABI v1, а не по байтам 0.2.4.
- Проверяющий независимо принимает исходный адресный замер до изменения и повторяет тот же benchmark и тесты после него, сверяет контрольные суммы с текущим эталоном и оставляет команды, результаты и вывод. Операция получает `DONE` после независимой приёмки результата на Windows, Pixel 3 и Web с учётом документированной доступности 0.2.4/Web. При устойчивом отставании исполнитель прикладывает профиль, причину и следующий вариант; карточка остаётся открытой до решения. Отложенная общая приёмка не заменяет пооперационную.
- Для native изменений сохраняются `yuv_*_v1`, структуры, статусы и допустимая матрица форматов. Проверки адресов и переполнений выполняются до fast path; ошибки не оставляют частично записанный destination. Сохраняются BT.601, округление, alpha, ROI, edge-replicate, footprint chroma 2×2, odd geometry, row/pixel stride и padding. На каждом C-шаге проверяются профильные Windows native/reference тесты и доступные локальные проверки границ; sanitizer и 32-битный runtime входят в поздние платформенные gates. Общий полный gate — PERF-38. Сгенерированные bindings вручную не править.
- Web остаётся частичной WASM-реализацией. Производительность Web измеряется в браузере отдельно от native; после каждой затрагивающей C правки пересобираются и проверяются WASM assets для адресного замера, PERF-36 сверяет конечные assets. Для Gaussian допускается смена алгоритма только при byte-exact результате. Если разделимая схема даёт отличия, сохранить текущий контракт и вынести возможную смену семантики на отдельное решение.
- До изменения native C исполнитель показывает конкретный план реализации и проверок и получает явное разрешение владельца согласно `AGENTS.md`. Подготовка стенда, измерения и проверки идут без правок native C.

Приоритет по наблюдаемой задержке: PERF-02 (вертикальный flip), PERF-14/15 (кадровая конвертация), PERF-25—27 (blur). Это рекомендация для выбора при старте, а не заранее назначенный порядок; профили и возможности платформ могут изменить выбор. Зависимости в таблице обязательны; перед `IN_PROGRESS` у выбранной PERF-карточки должен быть добавлен ID её принятой MEAS-карточки. Следующая операция начинается после `DONE` предыдущей. Статусы функций: `TODO` → `BASELINE_REVIEW` → `IN_PROGRESS` → `REVIEW` → `DONE`. `DONE` требует проверки после изменения на тех же платформах. Остальные задачи переходят из `REVIEW` сразу в `DONE` после независимой приёмки.

#### MEAS-02 — Pixel 3 и Web runner readiness

**Статус:** IN_PROGRESS
**Исполнитель:** OpenAI `gpt-5.6-terra`, reasoning medium
**Приёмка:** OpenAI `gpt-6-sol`, итоговая проверка MEAS-02 и MEAS-03
**Зависимость:** MEAS-01

**Решение:** расширить существующий Dart benchmark для Android release и Flutter Web в поддерживаемом JS режиме. Переиспользовать сценарии, генератор входа, контроль входных SHA и CSV-контракт MEAS-01. В Web вызывать пакетный WASM backend; не заявлять полную parity. Недоступный в конкретной версии/backend сценарий записывать как `UNSUPPORTED` с причиной. Таймер охватывает только один публичный вызов; создание изображения, восстановление входа и checksum остаются вне таймера.

**Объём:** только `tool/bench/` и `doc/perf/`; не менять API пакета, `lib/`, native C/CMake или bindings. Сборки и результаты держать вне каталога репозитория или в явно указанном evidence каталоге. Не менять/удалять пользовательские данные Pixel 3; обновлять APK только через `adb install -r`.

**Готово, когда:** Android release APK и Web JS runner воспроизводимо собираются для 0.2.4 и ABI v1 SHA `35c516e216fef8d5ed4ef379d38655fc643f738d`; оба принимают те же scenario IDs и ожидаемые входные SHA; адресный smoke `FLIP.I420.V` записывает сырые строки, timings, checksum, версии/toolchain и статус; ошибки процесса дают строку ошибки и ненулевой итог; команды и реальные ограничения описаны. Browser runtime должен быть реально запущен; сборка без запуска не считается Web smoke. Не устанавливать/очищать приложение с потерей данных.
