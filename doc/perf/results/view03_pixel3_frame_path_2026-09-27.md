# VIEW-03: полный путь «получен кадр → показан кадр» на Pixel 3

**Третий проход**, ответ на решение архитектора после отказа второго прохода (условия и решение —
в todo.md, секция VIEW-03). Второй проход разделял `delivered`/`accepted`/`presented` по разным
прогонам — архитектор указал, что это разные сигналы (`delivered` под холостым слушателем не равен
`delivered` внутри реально работающего превью), и что медиана `transform → показ` (33–41 мс) не
объясняет период между показами (~150–160 мс): свыше 110 мс оставались неучтёнными.

**Дополнение к третьему проходу:** единая подписка нашла и точно локализовала узкое место
(`applyRotation`), но заявленное объяснение «специфично для операции rotate» показалось
неправдоподобным пользователю — на одном native пути разница в 10× между rotate и flip выглядела
странно. Проверка нашла настоящую причину: не сама операция, а **padding входного кадра** (раздел
«Причина найдена» ниже). Итоговые числа раздела «Результат» не изменились, изменилось объяснение.

Устройство: `adb devices -l` → `8B1X11QLW device`, Pixel 3, Android 12, arm64-v8a. Экран включён,
`mWakefulness=Awake`, `mIsPowered=true`, `mStayOn=true` на время прогонов.

## Методология: диагностика внутри единственной реальной подписки

По решению архитектора добавлен узкий диагностический callback внутри
`_YuvCameraPreviewMobile.onNewImageAvailable` — единственной платформенной подписки mobile-превью,
не второй параллельный слушатель. Реализация:

- `example/lib/widgets/impl/yuv_camera_preview_io.dart`: `DebugYuvCameraPreviewMobileEventKind` (enum),
  `debugYuvCameraPreviewMobileEvent` (sink, `null` по умолчанию — никакой стоимости в проде) и
  `debugYuvCameraPreviewMobileClock` (общий монотонный `Stopwatch`, стартует только в тесте).
- `example/lib/widgets/impl/yuv_camera_preview_mobile.dart`: событие `delivered` — вход в
  `onNewImageAvailable`, до какой-либо проверки; `droppedBeforeTransform` (`reason: 'stale'`/`'busy'`) —
  кадр отброшен до `transform`; `yuvImageReady` — сразу после `CameraImage.toYuvImage()`, до поворота;
  `rotationApplied` — после `applyRotation`, до `applyFlipHorizontal`; `acceptedForTransform` —
  непосредственно перед вызовом `presentCameraFrame` (который вызывает публичный `transform`).
  `presented` — существующий публичный `onFramePresented`, читается тестом на той же шкале времени,
  отдельного хука не требует.

Хук — единственная правка `lib/`? Нет: `lib/` не тронут вовсе, всё выше — в `example/lib/`, как явно
разрешило решение архитектора («менять публичный API `lib/` для этого не требуется»; хук — временный
диагностический, «можно убрать после измерения»). Это **та же** подписка, которую использует реальный
`YuvCameraPreview` — хук только фиксирует метку времени, не задерживает и не дублирует работу на пути
кадра, поэтому delivered/dropped/accepted здесь — счётчики одного живого, работающего превью, а не
холостого слушателя, как в отклонённом втором проходе.

`flutter drive` не поддерживает `--release` на non-web («Use --profile mode for testing application
performance») — то же ограничение инструмента, что и во всех предыдущих Pixel 3 карточках; `--profile`
(AOT без debug-assert) — практический потолок задачи здесь.

```
adb shell dumpsys power | grep -E "mWakefulness|mScreenOn"
flutter drive --driver=test_driver/integration_test.dart \
  --target=integration_test/view03_frame_path_pixel3_test.dart -d 8B1X11QLW --profile
```

## Разбор интервалов (те же два прогона)

| Интервал | Прогон 1, медиана | Прогон 2, медиана | Что это |
| --- | ---: | ---: | --- |
| `to_yuv_image_us` | 1,42 мс | 2,08 мс | `CameraImage.toYuvImage()` — копирование плоскостей |
| `rotation_us` | **93,64 мс** | **93,96 мс** | `applyRotation()` — сам поворот |
| `flip_us` | 8,07 мс | 8,07 мс | `applyFlipHorizontal()` |
| `accepted_to_presented_us` | 38,89 мс | 29,61 мс | `transform` + decode + draw внутри presenter |
| `presented_gap_us` | 152,68 мс | 149,12 мс | период между двумя показанными кадрами |

**Найдено и дважды воспроизведено с точностью до десятых: `applyRotation()` — реальное узкое место,
а не `applyFlipHorizontal()`, не decode/`ChangeNotifier` и не сама доставка кадров камерой.**
`to_yuv_image_us` (1,4–2,1 мс) и `flip_us` (8,1 мс, оба прогона идентичны) — на порядок дешевле;
`accepted_to_presented_us` (30–39 мс) — сравним с decode+draw, ожидаемо. `rotation_us` (~94 мс) — в
10 раз дороже flip'а, хотя оба идут через один и тот же путь диспетчеризации: современный публичный
`applyRotation`/`applyFlipHorizontal` (`lib/src/yuv/impl/io/yuv_image.dart:478,490`) — это тонкая
обёртка с capability-проверкой (`_requireCapability`) вокруг `legacyRotate`/`legacyFlipHorizontal`
(строки 204, 226) — тот же метод, что был публичным в API 0.3.0, сохранённый под этим именем как
контракт `YuvLegacyDispatchAdapter`, не отдельная более старая или более медленная реализация. Оба
в итоге вызывают ровно один native символ через `YuvAbiV1Runner.rotate`/`.flip` — единственный путь,
без параллельного «современного» и «legacy» native-исполнения. Прочитано, не изменено — per AGENTS.md
native C не трогать без явного разрешения. Разница именно между rotate и flip на одном и том же пути —
специфичная, воспроизводимая находка, не общее замедление всего диспетчера: если бы дело было в общем
per-pixel overhead, flip стоил бы похоже, а он не стоит.

Арифметика согласуется: `presented_gap_us` (149–153 мс) ≈ `rotation_us` (94 мс) + `flip_us` (8 мс) +
`accepted_to_presented_us` (30–39 мс) + время ожидания следующего доставленного кадра, пока presenter
был занят (кадры между `busy`-дропами). Все составляющие decode+draw пути теперь учтены — открытого
разрыва «110 мс неучтённых», который отклонил второй проход, больше нет.

## Причина найдена: row padding входного кадра, не decode/draw, не общая ABI v1 регрессия

Первая версия этого раздела (см. историю в todo.md) предполагала, что дороговизна специфична для
`applyRotation` как таковой, отличая эту находку от документированной в памяти проекта
(`native-perf-regression-0-4`) регрессии, которая на 1080p замедляла flip и rotate **одинаково**.
Пользователь усомнился в правдоподобности разницы 10× между rotate и flip на одном native пути и
попросил перепроверить прямым измерением — эта проверка нашла настоящую причину.

**Изоляция, четыре последовательных шага, каждый на реальном устройстве:**

1. **Чистый Dart FFI, синтетический вход, без камеры и без Flutter widget-дерева**
   (`example/integration_test/rotate_vs_flip_pixel3_test.dart`, 720×480 I420, тот же `YuvImage.i420(...)
   ..applyRgbaBytes(...)`, что и во всех прежних синтетических тестах этого проекта): `rotation_90` —
   12,6 мс, `rotation_180` — 11,3 мс, `rotation_270` — 11,6 мс, `flip_horizontal` — 6,0 мс. **На порядок
   меньше** ~94 мс, найденных внутри mobile-превью — сам факт разницы между «в превью» и «в изоляции»
   стал следующим вопросом. Raw —
   [`view03_pixel3_raw/adhoc_rotate_vs_flip_synthetic.json`](view03_pixel3_raw/adhoc_rotate_vs_flip_synthetic.json).
2. **Реальный, живой поток камеры, без widget-дерева** (`rotate_under_camera_load_pixel3_test.dart`):
   `applyRotation` на настоящих кадрах с фронтальной камеры (`sensorOrientation=270`) — **92,6–93,3 мс**,
   то есть исходная находка воспроизведена без presenter/`ChangeNotifier`/build pipeline вообще. Останов
   потока (`subscription.cancel()`, пауза 200 мс) и повторный поворот **того же самого** сохранённого
   кадра дал **92,8 мс** — идентично «живому» замеру. Конкурентная нагрузка живой камеры исключена как
   причина: разница не в параллельной работе, а в самом кадре. Raw —
   [`view03_pixel3_raw/adhoc_rotate_under_camera_load.json`](view03_pixel3_raw/adhoc_rotate_under_camera_load.json).
3. **Диагностика геометрии того же реального кадра**: `yPlane.bytesPerRow = 768` против
   tight `width * pixelStride = 720` — **48 байт паддинга на строку** (Y-плоскость), которого нет у
   синтетического входа шага 1 (`YuvImage.i420` всегда строит tight-packed плоскости).
4. **Прямая проверка гипотезы, синтетический вход обеих геометрий, идентичный контент**
   (`rotate_padding_isolated_pixel3_test.dart`): tight `bytesPerRow=720` — **10,2 мс**; padded
   `bytesPerRow=768` (та же ширина/высота/содержимое, только 48 байт паддинга на строку) — **69,9 мс**.
   **7-кратное замедление вызвано исключительно 48 байтами паддинга на строку**, ничем другим. Raw —
   [`view03_pixel3_raw/adhoc_rotate_padding_isolated.json`](view03_pixel3_raw/adhoc_rotate_padding_isolated.json).

**Итог причины:** `applyRotation()` в native ABI v1 работает быстро (~10–13 мс на 720×480) на
tight-packed входных плоскостях и на порядок медленнее (~70–94 мс) на padded — при абсолютно одинаковых
ширине, высоте и содержимом пикселей. `applyFlipHorizontal()` на том же tight-packed синтетическом входе
даёт 6–8 мс, но не проверялся отдельно на padded входе в этой сессии — открытый пункт ниже.
`_sameGeometryDestination`/`_isTightLayout` (`lib/src/yuv/impl/io/abi/yuv_abi_v1_runner.dart:96-111,296-301`,
прочитано, не изменено) определяют tight-стрейд только для **destination**-аллокации на Dart-стороне
(`zeroFillDestination`), не выбирают native symbol или путь внутри native кода по геометрии **источника**
— то есть сам факт, что source padding так сильно замедляет just rotate, а не другую операцию, лежит
внутри native `yuv_kernel_v1.c`, куда эта измерительная карточка по мандату VIEW-03 и AGENTS.md
(native C не трогать без явного разрешения) не заходит. Найдена точная, дважды подтверждённая причина,
не диагностировано её устройство внутри native кода.

**Что это не означает:**

- **Не decode/draw, не `ChangeNotifier`/vsync.** `accepted_to_presented_us` (30–39 мс) в разумных
  пределах — узкое место раньше в пути, до презентера вообще. Гипотеза про `ChangeNotifier`, которую
  пользователь предложил во втором проходе, не подтверждается.
- **Не подтверждённая связь с `native-perf-regression-0-4` как «тот же самый» дефект.** Эта память
  документирует замедление на **1080p** как generic-per-pixel-driver overhead, одинаковый для flip и
  rotate. Здесь на 720×480 с **tight** входом flip (6–8 мс) и rotate (10–13 мс) — в разумных пределах
  друг от друга, никакой аномалии; аномалия появляется только с **padded** входом и специфична для
  rotate в этом эксперименте (flip на padded входе не проверялся). Связь с той памятью, если она есть,
  не установлена этой карточкой — это вопрос для дальнейшего архитектурного разбора, не факт.

## Для архитектора: варианты решения и требование к документации

Два направления обсуждались с пользователем, оба вне мандата этой измерительной карточки:

1. **Исправить native `applyRotation` так, чтобы padded вход не терял в 7 раз** — системное решение,
   устраняет причину, а не только её видимое следствие; требует правки `yuv_kernel_v1.c`/ABI v1 и,
   по AGENTS.md, отдельного явного разрешения пользователя, плана и объяснения перед началом.
2. **Перепаковать (repack) входные плоскости в tight-stride на границе создания `YuvImage`** —
   например, в `YuvImage.i420(..., planes: ...)`/`YuvImageImpl` конструкторе, а не только в
   `example/lib/ext.dart` `toYuvImage()`: унифицирует обход для всех потребителей пакета, не только
   example. Цена — одна memcpy-копия на кадр (порядка 1–2 мс по замеру `to_yuv_image_us` в этом же
   отчёте), в 30–60 раз дешевле проигрыша на rotate. **Если архитектор выберет этот путь: repack —
   наблюдаемое изменение поведения конструктора (padded входной буфер больше не хранится как есть,
   а копируется в новый tight-packed буфер), и по прямому требованию пользователя это должно быть
   явно прописано в README и dartdoc конструктора, а не быть скрытым побочным эффектом** — потребитель,
   передающий свой собственный padded `Uint8List` в `planes:`, должен явно знать, что либо (а) его
   буфер больше не aliased этим `YuvImage` (репак его копирует), либо (б) padding сохраняется как
   договорено сейчас — какой из двух вариантов архитектор выберет, тот и должен попасть в
   документацию первым же коммитом, который меняет это поведение.

## Итог

- **Показанный FPS candidate — 6,40–6,59** объяснён полностью, без неучтённого остатка: узкое место —
  **`applyRotation()` на padded входном кадре** (медиана ~93 мс на реальном 720×480 кадре камеры), не
  `applyFlipHorizontal()` (~8 мс на tight синтетике), не decode+draw внутри presenter (~30–39 мс) и не
  доставка кадров камерой (платформа физически доставляет быстрее, чем реальная подписка успевает
  обработать — 14,5–15,7 Гц внутри рабочей подписки против ~30 Гц в изолированном холостом прогоне
  второго прохода, что и предсказал архитектор).
- Presenter не роняет ни одного принятого кадра сам (`accepted == presented` в обоих прогонах);
  доставленные кадры отбрасываются мобильным гейтом `isBusy` **до** `transform` — потому что предыдущий
  кадр всё ещё проходит через `applyRotation`.
- **Причина найдена и дважды прямо подтверждена изолированным экспериментом (не гипотеза): 48 байт
  паддинга на строку (`bytesPerRow=768` против tight `720`) дают 7-кратное замедление `applyRotation`
  на идентичном контенте и геометрии (10,2 мс → 69,9 мс).** Это разрешает противоречие, которое
  пользователь заметил в предыдущей версии этого отчёта: там разница rotate/flip в 10× на одном native
  пути выглядела неправдоподобной сама по себе — оказалось, дело не в операции per se, а в том, что
  синтетический тестовый вход всегда tight-packed, а реальный камерный кадр — padded.
- Гипотеза пользователя про `ChangeNotifier`/vsync не подтвердилась этим измерением как причина низкого
  FPS — узкое место раньше в пути, чем presenter.

## Открытые пункты

1. `applyFlipHorizontal` не проверялся на padded входе в этой сессии — неизвестно, страдает ли он от
   того же паддинга, что и `applyRotation`, или дороговизна padded-input специфична именно для rotate.
2. Устройство причины внутри native `yuv_kernel_v1.c` (почему padded source так сильно замедляет именно
   этот путь) не диагностировано — измерительная карточка нашла и дважды подтвердила точную причину на
   уровне наблюдаемого поведения, не заглянула внутрь native кода; правка native C требует отдельного
   явного разрешения пользователя per AGENTS.md.
3. Решение (исправить native kernel или репаковать входные плоскости на границе создания `YuvImage`) —
   архитектурный вопрос, переданный отдельно, см. раздел «Для архитектора» выше; если выбор — repack,
   изменение поведения конструктора должно быть явно задокументировано в README и dartdoc по прямому
   требованию пользователя, не оставлено скрытым побочным эффектом.
4. `--release` недоступен через `flutter drive` на non-web — ограничение инструмента.
5. Web и desktop пути не измерялись — задача явно про Pixel 3.
6. Baseline не проверялся на «доставлено платформой» отдельно от «принято» этим же методом (единой
   подписки) — исходный код `9d14f83` использует другой, не через `CameraPlatform.instance` напрямую,
   путь потока, так что этот диагностический хук к нему неприменим без отдельной адаптации.
7. Причина дрейфа single-snapshot PSS между последовательными прогонами (предыдущий проход) осталась
   неустановленной; не пересматривалась в этом проходе.
8. Диагностические хуки/файлы оставлены для воспроизводимости, `null`/не влияют на прод-путь по
