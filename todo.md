## Цель и границы цикла

- `yuv_ffi` сохраняет существующий публичный API: изображения, операции, native/WASM backend, геометрию, `YuvImageWidget`, `YuvImageProvider`, `YuvFramePresenter`, `YuvFrameView`, рендерер и шейдер. Перенос камеры не меняет алгоритмы native C или WASM-артефакты.
- `yuv_camera 0.0.1` зависит от `yuv_ffi`; обратной зависимости нет. Публичный API камеры: `YuvCameraFrame`, `YuvCameraFrameSource`, `YuvCameraView`, `YuvCameraViewController`, `YuvTransformView`. Импорт кадров, вычисление камерной ориентации и управление потоками — внутренние реализации.
- `yuv_ffi/example` демонстрирует обработку и отображение изображений без `camera`, `camera_desktop`, `camera_platform_interface` и ML Kit. Камерные экраны, ML Kit-адаптер, распознавание лиц, их UI и демонстрационное размытие переходят в пример `yuv_camera`; редактор YUV остаётся здесь без распознавания лиц.
- ML Kit не входит в обязательные зависимости `yuv_camera`: обработчик подключается через `onFrame`; отдельный интеграционный пакет в этот цикл не входит. Desktop-провайдер камеры регистрируется приложением (A1 подтверждён: `doc/camera-extraction.md`, раздел 6); граница зависимостей и публичного API — там же, раздел 1.
- Камерные тесты, helpers, бенчмарки и CI-сценарии переходят вместе с камерой. Проверки YUV, ABI, native/WASM, геометрии, презентера, шейдера, reference и производительности операций остаются здесь, включая интеграционные тесты в `example/`.
- Смешанные сценарии разделяются по проверяемому поведению. Синтетический поток `YuvImage` не считается камерным тестом. Проверки не удаляются только ради облегчения зависимостей.
- Совместимость пары `yuv_ffi 0.5.2` / `yuv_camera 0.0.1` подтверждается отдельным потребителем с обеими зависимостями и проверками перенесённой камеры. Основной пример `yuv_ffi` остаётся независимым от камеры.

## Правила текущего цикла

Общие роли, переходы статусов, отчёты и завершение работы — `D:\.projects\ENGINEERING_PROTOCOL.md` и файл своей роли в `.protocol/`. Проектные ограничения, пробы, команды и CI — [AGENTS.md](AGENTS.md). Здесь остаются только правила ведения этого выпуска и проектные исключения:

1. Этапы выполняются по очереди, карточки — по зависимостям. Заморозка кандидатов — на этапе 2. Architect полностью расписывает карточки этапа до начала исполнения.
2. Работа последовательная, прямо в `dev`, без worktree и веток пула (D-22, D-25). Базовый SHA пула — в первой карточке; диапазон ревью — `<base>..<SHA>`.
3. Карточки — `tasks/0.5.2/<ID>.md`; в тексте ID через неразрывный пробел: PREP 1. Карточка и дашборд обновляются вместе. После приёмки — `DONE`, одна строка в `COMPLETION.md`, карточка и строка дашборда удаляются. Это проектное исключение из общего перехода через `ACCEPTED`.
4. Проверки задаются карточкой и `scope_guard.sh`; результат принимается только после завершения команды с exit code и критерием скрипта. Reviewer читает diff и отчёт; дополнительные запуски — по карточке и правилам роли.
5. При отказе CI фиксируются SHA, workflow/run/job, шаг и фрагмент ошибки; Engineer получает факты. Исследование причины — отдельное поручение. Временные `ci/*` теги удаляются в конце этапа или после выпуска; ссылки на запуски сохраняются.
6. Внешняя документация, dartdoc, комментарии кода/workflow, ошибки и коммиты — на английском. План, карточки, отчёты и внутренние документы — на русском (D-7).
7. Выпуск — Engineer: аннотированный тег `<версия>` без `v` на кандидате `release/<версия>`; `main` переводится fast-forward на тот же SHA, без merge-коммита. При расхождении `main` включается в `dev`.
