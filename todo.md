## Активные задачи: виджет и превью

Цель — корректно показывать и захватывать кадры при длительной работе камеры, затем измерить полный путь кадра на устройстве. Работа ограничена Dart/Flutter кодом `lib/src/widgets/`, публичным экспортом виджетов, `example/lib/widgets/`, их прямыми вызовами и зависимостями/конфигурацией example; native C и ABI v1 не входят в эти карточки. Для каждой выполненной карточки нужны короткий отчёт, независимая проверка и отдельный коммит. Тир указан для исполнителя и ревьюера; конкретную модель выбрать при старте задачи.

### Executor Report

**Состояние до правки** (прослежено по коду после VIEW-01B; дефекты 2–4, 6 и 7 подтверждены негативным
контролем — тесты падают на коде без правки соответствующего места):

1. *Контракт `transform` по показу уже был общим.* Все три превью делали `transform?.call(frame) ?? frame` →
   `presenter.present`, desktop после VIEW-01B — тоже (`RTCVideoView` удалён). `CameraScreen.imageCapturer`
   копирует и возвращает тот же кадр, то есть захватывается показанный кадр.
2. *Ошибка в `transform` обрабатывалась по-разному.* Mobile/desktop: `debugPrint`, кадр отброшен, поток идёт.
   Web TrackProcessor: исключение уходило в `onError` цикла чтения — превью навсегда заменялось текстом ошибки,
   дорожки камеры оставались включены; web scheduler — то же плюс `_stopLoop`.
3. *Mobile, рестарт.* `didUpdateWidget` сразу звал `startImageStream`, не дожидаясь `stopImageStream` прежнего
   потока (desktop ждёт `previousStop` с VIEW-01B). Смена A→B→A при ещё идущей остановке A давала второго
   слушателя той же камеры.
4. *Mobile, ошибки старта.* Неинициализированный контроллер: `initState` бросал `ArgumentError` из не
   ожидаемого `Future` (необработанное async-исключение), в `didUpdateWidget` — ранний `return` без
   `super.didUpdateWidget` и пустое превью. Ошибка `startImageStream` (`CameraException`) в `initState` —
   необработанное исключение, в `didUpdateWidget` — молча поглощалась `.ignore()`. Ошибка не показывалась.
5. *Web, `await` при старте* (открытый пункт VIEW-01): `dispose` или рестарт во время `getUserMedia`/`play()`
   не проверялись — полученный после закрытия поток присваивался `_mediaStream` и не останавливался (камера
   горит), `_running = true` и старт цикла на закрытом состоянии; два одновременных `_startStream` запускали
   два reader с одним поколением; ошибка старого старта писалась в `_lastError` нового.
6. *Ошибка камеры не останавливала поток.* Web: ошибка чтения — текст ошибки, дорожки не остановлены.
   Desktop: ошибка потока — текст ошибки, подписка `camera_desktop` не отменена, кадры продолжали приходить.
7. *`CameraScreen`.* Второе нажатие «Capture» до кадра заменяло `captureCompleter` — первый `takePicture`
   не завершался никогда (открытый пункт VIEW-00/01B); закрытие экрана при ожидающем захвате — то же.

**Правка:**

- `example/lib/widgets/present_camera_frame.dart` (новый, без `dart:html`): `presentCameraFrame(presenter, frame,
  transform)` — единственный путь кадра в презентер на всех платформах. Показывается результат `transform`,
  без него — кадр камеры; исключение `transform` или конвертации — `FlutterError.reportError`, отбрасывается
  только этот кадр, презентер свободен, поток не останавливается. Контракт описан в dartdoc
  `YuvCameraPreview.transform` (в т.ч. «для захвата показанного кадра храните возвращённый кадр через `copy()`»).
- `example/lib/widgets/stream_start.dart` (новый, без `dart:html`): `runStreamStart` — `open` → `attach` →
  `onStarted` с `isCurrent`, проверяемым после каждого `await`: поток, открытый для неактуального старта,
  уходит в `release`; неактуальный старт не вызывает `onStarted`; его ошибка не доходит до `onError`. Вынесен
  по образцу `runFrameReadLoop` (VIEW-01), чтобы проверять гонки в VM.
- Web: `_startStream` через `runStreamStart`, `isCurrent` = `mounted && generation == _streamGeneration`
  (поколение захвачено синхронно при старте; рестарт и `dispose` его повышают). Новый `_failStream` для ошибки
  текущего потока (старт, цикл чтения, canvas): `_stopLoop`, `_stopMediaTracks`, `presenter.reset`, текст
  ошибки. Оба пути кадра — через `presentCameraFrame`.
- Mobile: переписан по схеме desktop. Превью отслеживает контроллер, поток которого запустило само
  (`streamingController`, `streamStarted`), а не `isStreamingImages`; `super.didUpdateWidget` первым; рестарт
  ждёт `previousStop`; неинициализированный контроллер и ошибка `startImageStream` показываются текстом
  `Camera error: …`, ошибка устаревшего старта только логируется. Остановка синхронная, если старт прошёл
  (`isStreamingImages`): `CameraScreen` освобождает контроллер сразу после превью, а `stopImageStream`
  на освобождённом контроллере бросает (регрессия найдена тестом по ходу работы и закрыта, см. тесты 9–12).
- Desktop: ошибка потока текущего поколения — `stopStream()` + `presenter.reset()` перед показом текста.
- `yuv_camera_preview_io.dart`: выбор mobile/desktop по `Platform.operatingSystem`, как раньше, но в debug
  приоритет у `debugDefaultTargetPlatformOverride` (release его игнорирует, как и Flutter). `defaultTargetPlatform`
  не подходит: в любом `flutter test` он Android. Override — ровно то, что проверяет assert
  `CameraController.startImageStream`, поэтому mobile-путь в VM идёт через настоящий `CameraController`.
  Ветка поворота Android использует тот же выбор.
- `CameraScreen`: повторное нажатие присоединяется к ожидающему захвату; `dispose` завершает ожидающий
  захват `null`.
- `CHANGELOG.md` 0.4.2 — одна строка в Changes; версия `pubspec.yaml` уже 0.4.2.

### Независимое ревью 27.09.2026 — TODO

Проверены `c1f4535` и `edb34ee`. Локально прошли 31 новый тест жизненного цикла и
`flutter analyze lib test --no-pub` в example; `flutter build web --no-pub` успешно
собрал JavaScript-версию (WASM dry run сообщил о прежнем `dart:html`). Тесты
подтверждают ожидание остановки mobile-потока, освобождение устаревшего web-старта,
пропуск кадров и защиту от двойного Capture. Реальные браузер и Android-устройство
в этом ревью не запускались.

**Условия повторной приёмки:**

1. `CameraScreen.imageCapturer` завершает `captureCompleter` прямо в `transform`, до
   `YuvFramePresenter.present`, асинхронного декодирования и кадра отрисовки. При смене
   контроллера, ошибке декодирования или `presenter.reset()` в этот промежуток
   `takePicture` всё равно вернёт кадр через 500 мс, хотя он не был показан. Это
   противоречит критерию «захватить именно показанный кадр» и уже признано в открытом
   пункте 5 отчёта исполнителя. Привязать подтверждение захвата к факту отрисовки
   конкретного кадра и отменять ожидающий захват при сбросе/остановке потока;
   добавить регрессионный тест смены потока между `transform` и draw.
2. Ошибка `onStreamedFrameAvailable` после успешного старта mobile-потока остаётся
   необработанной: `CameraController.startImageStream` в `camera` 0.11.0+2 создаёт
   подписку `.listen(onAvailable)` без `onError`, а новая mobile-ветка обрабатывает
   только ошибку старта. Это не просто отсутствие текста ошибки: асинхронная ошибка
   потока может уйти в зону без остановки камеры. Карточка требует обработать
   ошибку камеры и остановить поток. Выбрать поддерживаемый путь получения ошибок,
   остановить текущий поток и проверить поведение тестом fake `CameraPlatform`.

После этих исправлений повторить локальные тесты и анализ example. Браузерный и
Android runtime smoke нужны для предрелизной проверки, но сами по себе не заменяют
закрытие двух воспроизводимых контрактных дефектов выше.
