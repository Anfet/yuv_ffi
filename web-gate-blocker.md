# Web-гейт: почему YUV-08, YUV-12 и YUV-13 сейчас не закрываются

Записка для независимого ревью. Дата: 2026-09-14. Ветка `fix/0.2.5-release-readiness`,
коммит `54d2a25`. Все числа ниже получены прогонами, ссылки на runs — реальные.

---

## Короткий ответ

Технического блокера больше нет: Web-рантайм **доказано работает** в браузере на CI.
Блокер теперь организационный — DoD трёх карточек предписывает инструмент
(`flutter test --platform chrome`), который для этих тестов физически непригоден,
и требует объём проверок, целесообразность которого стоит пересмотреть.

Нужно решение владельца по двум пунктам: **чем заменить инструмент** и
**сузить ли объём Web-матрицы**.

---

## 1. Что сломано в предписанном инструменте

DoD YUV-12 и «Проверка» YUV-08/YUV-12/YUV-13 требуют
`flutter test --platform chrome`. Этот раннер **не поднимает asset bundle**.

Измерено напрямую: поднят тестовый сервер раннера и опрошен HTTP-запросами.

```
200  /static/index.html
404  /assets/packages/yuv_ffi/assets/wasm/yuv_ffi.js
404  /assets/AssetManifest.json
```

Загрузчик WASM инжектит `<script src="assets/packages/yuv_ffi/...">`, который
в этих условиях не резолвится никогда. Результат на CI (Linux, run #18):

```
Bad state: Failed to load WASM loader script:
assets/packages/yuv_ffi/assets/wasm/yuv_ffi.js
  at setUpAll (test/web/yuv_web_wasm_test.dart)
```

Следствия:

- дефект **не** Windows-специфичен: на ubuntu-latest ровно тот же отказ;
- дефект **не** в пакете: `assets: - assets/wasm/` в `pubspec.yaml` объявлен
  корректно, оба артефакта присутствуют (`yuv_ffi.js` 13579 B, `yuv_ffi.wasm` 39809 B),
  CI успешно собирает их через emsdk перед прогоном;
- ни один из четырёх сьютов `test/web/*` не может пройти этим раннером —
  все умирают в `setUpAll` до первого ассерта.

### Корректировка ранее записанного диагноза F-007

В карточке YUV-02 было записано: зависание на `loading` >90 s, причина —
«CanvasKit path формируется с несовместимыми разделителями», проявление
локальное для Windows. **Все три утверждения неверны.**

| Записано | Измерено |
|---|---|
| Зависает на `loading` | Падает детерминированно после browser timeout ~183 s: `Connection closed before test suite loaded` |
| Причина — CanvasKit paths | Chromium стартует штатно, DevTools цепляется (`DevTools listening on ws://127.0.0.1:...`); harness внутри страницы не отвечает manager websocket |
| Windows-специфично | Edge через `CHROME_EXECUTABLE` — тот же отказ; на Linux CI — тот же |

Контрольный эксперимент, отделяющий окружение от Flutter: чистый пакет с
`dart test --platform chrome` на той же машине и том же Dart 3.12.2 проходит
(«All tests passed!»). То есть браузер, websocket и browser-test инфраструктура
исправны; непригоден именно `flutter test --platform chrome` для тестов,
которым нужны ассеты.

## 2. Что уже доказано рабочим

`integration_test` драйвит настоящее собранное приложение, где бандл существует.
Добавлен пробный тест (`example/integration_test/wasm_bootstrap_test.dart`):
инициализация WASM + одна конверсия.

Результат на CI (run `34782706854`, job `web-integration-probe`): **success**.

```

integration_test/wasm_bootstrap_test.dart is being served at http://localhost:36487
Debug service listening on ws://127.0.0.1:38235/...

```

Путь к Web runtime evidence открыт. Осталось решить, **что именно** по нему гнать.

Побочно устранено по дороге:

- рассинхрон драйвера (`ChromeDriver only supports Chrome version 153 / Current

- VM-джоб не собирал нативную библиотеку: добавлен шаг CMake, `analyze-and-test-vm`

  reference-кейсов падали вместо скипа на хосте без библиотеки.

Оставшийся 31 failure — известные расхождения reference-матрицы
(`FORMAT-TO-*`, `EFFECT-*`, `BLUR-*`), все в `reference_native_conversions_test.dart`,

## 3. Вопрос об объёме: предложение сузить DoD YUV-12

### Аргумент владельца

C-код общий для всех платформ. Если операция корректна на Android/iOS/Windows,
её математика корректна и в WASM — это один и тот же скомпилированный алгоритм.
Значит достаточно проверить, что рантайм поднимается и вызов доходит, а остальное
делегировать результатам native-прогонов.

### Что в этом аргументе верно

Для **C-логики** — верно. Прогон 119 эталонных кейсов на Web ради проверки
математики конверсий дублирует native-матрицу YUV-11 без новой информации.

### Где аргумент не работает: контрпример YUV-08

Web и native зовут одни и те же C-функции (`yuv420_negate`, `bgra8888_negate`),
но через **разные слои маршалинга**: 719 строк `js_interop`/копирования в кучу
WASM против 814 строк FFI-указателей. Обвязка написана дважды и независимо.

Из карточки YUV-08, дословно:

> Публичный `toBgra8888()` обещает длину всегда `width * height * 4`.
> **Native implementation уже repack-ит padded BGRA rows. Web для `bgra8888`
> возвращает копию всей `yPlane.bytes`**, поэтому при `rowStride > width * 4`
> возвращает padding и нарушает контракт.

C-код здесь идентичен. На Android/iOS/Windows работает, на Web — нет, потому что
repack живёт в обвязке, и на Web его не написали. Делегирование по индукции
пропустило бы этот дефект в релиз. Смоук его тоже не ловит: он проявляется только
при `rowStride > width*4`.

И финальная строка той же карточки:

> Web edge tests покрывают padded I420/NV, **но не padded BGRA**.

То есть даже существующий Web-набор оказался недостаточен — не по количеству
тестов, а по непокрытой комбинации.

### Граница, по которой предлагается резать

| Категория | Где проверять | Обоснование |
|---|---|---|
| Математика конверсий, точность crop/rotate/flip | только native (YUV-11) | один и тот же скомпилированный C |
| Геометрия, strides, padded layouts, контракты возврата | **обязательно Web** | обвязка написана дважды; здесь живёт YUV-08 |
| Жизненный цикл загрузчика: кэш, гонки, retry | **обязательно Web** | к C отношения не имеет вообще |

Конкретно: перенести в `integration_test` ~15 тестов (весь
`wasm_loader_initialization_test.dart` — 7 тестов; из `wasm_parity_edge_cases_test.dart` —
padded layouts, custom strides, `getBytes`-контракт, размеры 1x1 / 3x5 / 127x255).
Не переносить ~9 тестов round-trip качества и точности трансформаций.

Объём переноса: ~400 строк вместо ~890.

## 4. Что конкретно требуется от ревьюера

**Решение 1 — инструмент.** Заменить во всех затронутых DoD и секциях «Проверка»
`flutter test --platform chrome` на `flutter drive` + `integration_test`.
Обоснование — раздел 1: предписанный инструмент не поднимает ассеты, и это
свойство раннера, а не дефект пакета. Затронуты YUV-02, YUV-08, YUV-12, YUV-13.

**Решение 2 — объём Web-матрицы.** Один из вариантов:

- **2a. Сузить DoD YUV-12** по границе из раздела 3: Web проверяет обвязку,
  native — математику. DoD YUV-13 это уже допускает формулировкой
  «либо явно документированной platform limitation» — сужение оформляется как
  такая limitation с обоснованием.
- **2b. Оставить полную матрицу** — перенести все 119 кейсов на `integration_test`.
  Дороже, но буквально соответствует текущему DoD YUV-12
  («все строки обязательной матрицы реально исполняются с `kIsWeb == true`»).
- **2c. Перенести YUV-12/YUV-13 в 0.3.0** — тогда в 0.2.5 Web покрыт смоуком,
  и это честно фиксируется в карточках как непроверенный parity.

**Замечание исполнителя.** Рекомендую 2a. Но отмечаю, что это моё суждение против
буквы действующего DoD: текущая формулировка YUV-12 требует полной матрицы, и
сузить её может только владелец. До решения YUV-08/YUV-12/YUV-13 остаются
`BLOCKED`, и YUV-18 вместе с ними.
