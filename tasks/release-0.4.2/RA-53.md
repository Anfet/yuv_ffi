# RA-53 — Маршрутизация CI по префиксу ветки
**Status:** IN_PROGRESS · **Tier:** T2 · **Execution Mode:** STANDARD · **Review Tier:** T1 · **Owner:** orchestrator: release CI and post-merge checks · **Depends On:** RA-52 · **Rejection Count:** 1

#### Problem / Goal
После RA-52 карточная ветка получает CI только ручным `workflow_dispatch`: исполнитель должен помнить про запуск, а по списку run не видно, какие платформы проверены. Решение Engineer D-5: набор джоб определяется префиксом имени ветки и запускается автоматически на push.

#### Architect Decision
Правка `.github/workflows/ci.yml` и новый `tool/ci/scope_guard.sh`. Шаги джоб, кроме добавленного первого шага проверки, не менять. `workflow_dispatch -f jobs=…` из RA-52 остаётся запасным путём.

#### Architect Decision — порядок приёмки маршрутизации (GPT-6 Sol, medium, 29.09.2026)
D-5 остаётся без изменений: для `.github/workflows/ci.yml` нужен префикс `all`. До merge Terra проверяет и отправляет реализацию в `all/RA-53`; полный CI и scope guard должны пройти, затем точный SHA передаётся независимому T1 ревьюеру. После T1 ACCEPT оркестратор условно вливает этот SHA в `release/0.4.2` и требует успешный полный release CI. Только после этого можно проверить маршрутизацию push от merged release SHA без изменения `.github/workflows/ci.yml` в тестовом diff. Оркестратор создаёт временные ветки только с marker-файлами для проверки узких маршрутов и scope guard. Если любой post-merge gate падает, merge откатывается, а RA-53 возвращается в REWORK. Временный merge в release до T1 ревью не делается.

**Имя ветки:** `<ключи>/RA-xx`, где `<ключи>` — один ключ или несколько через `+`. Ключи — те же, что в RA-52, плюс `all`:

| Ключ | Джобы |
| --- | --- |
| `all` | все 11 |
| `vm` | `analyze-and-test-vm` (обе версии) |
| `bindings` | `bindings-regeneration` |
| `linux` | `linux-native-smoke` |
| `macos` | `macos-native-smoke` |
| `ios` | `ios-native-build` |
| `android` | `android-native-build` |
| `windows` | `windows-native-smoke` |
| `web` | `wasm-web-integration` |
| `example` | `example-analyze-and-build` (обе версии) |

Примеры: `web/RA-41`, `windows+android/RA-90`, `all/RA-95`.

**Триггеры.**
- `push`: `release/**`, `main` — полный прогон (как в RA-52); карточные ветки — фильтры `branches` на `all/**`, `<key>/**`, `<key>+*/**`, `*+<key>/**`, `*+<key>+*/**` для каждого ключа. Прочие ветки, в том числе `ra/**`, CI на push не запускают. Прежние `paths-ignore` сохраняются.
- Условие каждой джобы (без отдельного job-маршрутизатора — он стоял бы в очереди того же раннера): джоба выполняется, если событие не `push`/`workflow_dispatch` на карточной ветке, или ветка `release/**`/`main`, или токен ключа найден в префиксе. Токен ищется с разделителями, чтобы `win` не совпал с `windows`: в строке `format('+{0}', github.ref_name)` есть `+<key>/` или `+<key>+`; то же для `all`. Логику dispatch из RA-52 сохранить через `||`.
- `concurrency`: как в RA-52 (без отмены на `release/**`).

**Проверка префикса (`tool/ci/scope_guard.sh`, bash — есть на всех трёх типах раннеров).** Первый шаг каждой джобы на карточной ветке; на `release/**`, `main`, `pull_request` и dispatch пропускается. Checkout с `fetch-depth: 0`. Скрипт вычисляет `base=$(git merge-base origin/release/0.4.2 HEAD)` и получает изменённые пути через `git diff --no-renames --name-only -z "$base" HEAD`, разбирая NUL-разделённый вывод без потери пробелов и переводов строк. Так проверяются обе стороны каждого rename: удалённый исходный путь и новый путь. Ошибки merge-base или diff завершают guard с ошибкой, не превращаясь в пустой список путей. По карте вычисляются требуемые ключи, и проверка падает с сообщением `scope: branch prefix '<prefix>' does not cover <keys> required by <path>`, если префикс их не покрывает (`all` покрывает всё). Изменение общего `.github/workflows/ci.yml` или общей инфраструктуры `tool/ci/` требует `all`. Поэтому RA-71…78 используют префикс `all` при удалении своих джоб из `ci.yml`; после миграции изменения, ограниченные отдельным платформенным workflow и его скриптом, получают узкий платформенный префикс.

**Правила (текст для правил 1–2 в `pre-release-todo.md` уже внесён архитектором):** ветка карточки — `<ключи>/RA-xx`; префикс выбирает исполнитель по карте, оркестратор сверяет при запуске; коммит негативного контроля проверяется джобами префикса, откат пушится только после завершения контрольного прогона, иначе concurrency его отменит.

#### T1 Review — REJECT
**Reviewer:** independent T1 reviewer  
**Reviewed implementation SHA:** `50f0f1ee790b042cd2343cd7df15b4d7cb300eff`  
**Executor report branch HEAD:** `3fd58a0082edbaa521a48cb1546566d1699bf54d`  
**CI:** [run 36552948924](https://github.com/Anfet/yuv_ffi/actions/runs/36552948924), success 11/11.  

**Finding:** `tool/ci/scope_guard.sh` enumerates changed paths with `git diff --name-only "$base" HEAD`. Git rename detection returns only the destination path. A move from a shared path such as `tool/ci/drive.sh` (requires `all`) to a narrower path such as `tool/ci/vm.sh` can therefore pass under a `vm` prefix while removing shared infrastructure. The reviewer reproduced Git's behavior on rename commit `bbe4324`: ordinary `--name-only` returned only the destination; `--no-renames --name-only` returned both paths.

The reviewer rejected the implementation because rename detection hid the removed shared path. The finding was escalated and resolved by the architect below. No merge or post-merge checks were performed. Rejection count: 1.

#### Architect Decision — rename coverage (GPT-6 Sol, medium, 29.09.2026)
D-5 requires the guard to cover both sides of renames; the prior `git diff --name-only` wording was an implementation sketch and does not change the invariant. Use `git diff --no-renames --name-only -z` with NUL-safe parsing, preserve fail-closed behavior for merge-base/diff errors, and do not redesign the path map. Before fresh T1 review, prove the required rename, narrow-path, deletion, and `all` controls from an isolated temporary repository. The rejected SHA remains rejected; do not merge it.
